# Release 0.5.0 (2026-09-28): one-time pads that can be handed over, a connect that can be stopped, and refusals that say why

0.5.0 merges the five client lines of work finished since 0.4.0, plus the
shared-Caddy deploy fix, into `master`. Commits:

- the merge history on `master` is 701d797 (`integrate/2026-09-28`, one merge
  per line);
- the release commits are on `release-0.5.0`.

The relay code is unchanged except its version. Everything users see is in
the web client and in the Android/iOS apps that bundle it.

## 1. What users will notice (read this first)

- **One-time pads (OTP) are made and handed over in their own sheets.**
  - **New pad, Export and Import each open a sheet** that says what happens
    next.
  - **On Android, Export offers "Share…"** (Quick Share, Bluetooth, …) and
    "Save to device"; Import opens the system file picker. Before this
    release, Import did nothing and Export produced no file on the phone.
  - The file name is neutral: `secure-chat-pad-YYYY-MM-DD-HHMM.json`, with no
    label and no pad id.
  - The transfer passphrase must differ from the pad passphrase. A weak
    transfer passphrase is warned about, not refused.
  - **Only the person who made a pad can export it.** A received pad cannot
    be exported again, because a third device would share a half of it (a
    two-time pad).
- **Both phones must run 0.5.0 before exchanging a pad.** A 0.4.0 importer
  still accepts a file re-exported by a receiver, so the "maker only" rule
  fully holds only once both sides are updated.
- **Two people on different pads are told so.** Example: both pressed New
  pad and both called it "Chess". Before, both saw "Ready" and every message
  arrived as undecryptable while each send used up pad. Now both are
  refused before "Ready" with "You and your contact picked different pads.
  This device used "Chess" (from your contact). …". Nothing is sent and no
  pad is used. If a pad was set up twice on one side, that is refused too,
  with a sentence of its own.
- **Two people on different security options are told so, on both sides.**
  - Example: one picked One-time pad, the other AES-256, DHKE or
    Post-quantum. Before, the OTP side went "Ready", AES-256 failed after
    15 s with "key confirmation failed", and DHKE/Post-quantum waited forever.
  - Now both sides read: "The relay may have altered this connection — or
    your contact picked X under Security options, while you picked Y. Agree
    with your contact, in person or on a channel you trust, which option you
    both use, then connect again."
  - The sentence names the relay first on purpose: the relay can alter the
    mode tag, and it must not be able to talk people into a weaker option.
- **Connecting can be stopped, and it ends by itself.**
  - A **Cancel** button sits beside Connect while a connection attempt has
    no answer yet.
  - A relay that never answers ends the attempt after **30 s**, and a
    contact lookup after **20 s**, each with a fixed sentence.
  - Before, a silent relay left Connect disabled until a reload (with an OTP
    pad locked).
- **A relay that starts a key exchange before letting us into the room is
  refused**, with a fixed sentence ("The relay passed on a key exchange
  before it had let you into the room …"). An honest relay never does this.
  It used to raise an invisible approval prompt and freeze the tab bar.
- **With a contact still on 0.4.0:**
  - OTP still connects. One line says the pads cannot be checked: "the other
    side runs an older version and cannot confirm that you both picked the
    same pad …" (owner decision 2026-09-28: warn, don't refuse).
  - A mode mix-up is named only on the 0.5.0 side. The 0.4.0 side behaves as
    before.
- **Nothing to migrate.** No stored format changed: contacts, chats,
  identities and pads open as they are. A pad file exported by 0.5.0 is
  the same format as before.

## 4. Deploy

```bash
# from a clean checkout of v0.5.0 (never the v0.4.0 tag's script: it
# installs deploy/Caddyfile over the shared /etc/caddy/Caddyfile wholesale)
bash deploy/deploy-2026-09-28-v0.5.0.sh
```

- **The relay is stopped briefly** (step 0b takes the DB backup). If the
  relay does not come back, step 3 rolls back by itself.
- **Caddy:** this deploy brings the shared-Caddy fix live. Step 4 installs
  deploy/Caddyfile plus the live file's marker blocks (Kiosk's). It
  validates before installing, restores on failure, and never touches
  `/etc/caddy/sites.d/`.
- **After the deploy:**
  - Kiosk's deploy may switch to `/etc/caddy/sites.d/kiosk.caddy`
    (nachrichtenapp).
  - Check that `kiosk.138-199-144-35.sslip.io` still answers; the script
    reminds you.
- **Checks** (step 5): healthz 0.5.0 locally and publicly; the served
  `app.js`, `crypto.js`, `durable.js` and `index.html` equal the checkout's;
  CSP; accounts before = after; ownership; the composed Caddyfile.

## 6. Rollback

**Relay only** (the box):

1. Back up the current state first; never overwrite the only copy.
2. Restore the code:
   - on the box: `tar -C /opt/secure-chat -xzf
     /root/secure-chat-pre-0.5.0/code.tgz`, then `chown -R root:root
     /opt/secure-chat/backend /opt/secure-chat/client`;
   - or `git checkout v0.4.0 -- backend client` in a checkout, then the
     script's copy and ownership steps.
3. `systemctl restart secure-chat`. The unit is the same file as 0.4.0's.

Notes:
- **Leave the Caddyfile.** The composed one serves 0.4.0 just as well, and
  the backup is a snapshot of a file other services write to.
- **Never run the v0.4.0 tag's deploy script.**
- **Keep the DB.** Nothing in 0.5.0 touched the relay's schema.
- **Clients follow a rollback** (no stored format changed). A 0.4.0 client
  loses what 0.5.0 added:
  - the pad check and the mode refusals;
  - Cancel and the deadlines;
  - the transfer sheets (0.4.0's Export/Import come back, still broken on
    Android).

## 7. Known limits and the next release

Documented, not fixed in 0.5.0:

- **A relay can switch the pad check off for one side with ONE frame.** It
  strips the offer, or injects an unchecked hello before Ready. That side
  shows the older-version line.
  - A loud version needs a per-pad "this contact checks" flag in the sealed
    pad record, which is an at-rest format change. Owner to decide.
- **A seated OTP side whose contact's proof never arrives waits** on
  "Waiting for the other party…" (Disconnect works). The join deadline ends
  at the relay's answer, so it does not cover this.
  - Next release: a "pad check did not complete" deadline, like key
    confirmation's 15 s (integration I-1).
- **A queued OTP guest can be taken to "Ready" by one relay hello.** This is
  pre-existing (0.4.0 went Ready on any hello). It fits the open owner
  option: refuse key frames while queued (integration I-2).
  - Recommended for the next release, before the deadline above.
- **A refusal on a seated connection whose Close the relay never answers**
  shows its sentence only when the browser gives up on the close (about
  60 s). Pre-existing class (integration I-3).
- **One maker file imported on two devices,** each talking to the maker,
  cannot be seen by a two-party check.
- **The chat bar does not show the pad's name.**
